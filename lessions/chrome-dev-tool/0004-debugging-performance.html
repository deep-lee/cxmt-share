Lesson 4: Debugging & Performance

Diagnose problems and measure what matters.

What You'll Learn

By the end of this lesson, you'll be able to capture console errors from any page, record and analyze Chrome performance traces, run Lighthouse audits, and emulate different devices and network conditions.

Knowledge: The Debugging Toolkit

Console-first debugging

When a page isn't working as expected, start here:

1. list_console_messages → see errors and warnings
2. list_network_requests → check for failed API calls
3. evaluate_script: document.title → verify page state
4. take_screenshot → confirm visual state

This is the debugging equivalent of "check the logs" — and it works on any page, even SPAs where the DevTools panel isn't available.

Performance traces

A performance trace records every event in Chrome during a page load (or interaction). The MCP server returns an automated analysis with actionable insights like:

  • LCP (Largest Contentful Paint) — when the main content appears
  • Document latency — how long the server took to respond
  • Render blocking — resources delaying first paint
  • Layout shifts — unexpected movement during load
performance_start_trace → (browser reloads) → performance_stop_trace
  → returns performance analysis with insight sets
Note: performance_start_trace can reload the page automatically. Use this to measure cold-load performance. The trace sends URLs to the CrUX API for real-user comparison (disable with --no-performance-crux flag).

Lighthouse audits

Lighthouse checks accessibility, SEO, and best practices. Use it when you need a full-page compliance report:

lighthouse_audit (mode: navigation, device: desktop)
  → returns scores and detailed recommendations

Results include scores (0–100) per category and a list of specific issues to fix.

Emulation

Test how pages behave under different conditions:

emulate (networkConditions: "Slow 3G", colorScheme: "dark")
→ now every page load uses throttled network

Network presets: Offline, Slow 3G, Fast 3G, Slow 4G, Fast 4G. You can also set custom geolocation, user agent, and viewport.

Emulation is sticky. Once set, it applies to all subsequent navigations on that page. Clear it by omitting the parameter (e.g., emulate with no networkConditions).

Knowledge: Memory Debugging

If you're debugging memory leaks (e.g., a page grows over time), use the heap snapshot tools:

take_heapsnapshot → captures current JS heap
get_heapsnapshot_summary → see memory by constructor
get_heapsnapshot_retaining_paths → find what keeps objects alive

This is an advanced feature. Enable it by starting the server with the --memoryDebugging flag.

Skill: Practice Tasks

Task A: Debug a failing page

Pick any site you know has errors (or use a test page):

Go to https://example.com, list the console messages,
then check if there are any network errors

Task B: Performance trace

Record a performance trace of https://developers.chrome.com
and tell me what's slowing down the page load

The agent will start a trace, reload the page, and return an analysis of bottlenecks.

Task C: Lighthouse audit

Run a Lighthouse audit on https://example.com
and tell me the top 3 accessibility issues

Task D: Emulate mobile

Go to https://example.com with a mobile viewport (375x667)
and take a screenshot. Then run a Lighthouse audit
on the mobile version.
